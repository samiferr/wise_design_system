There is no npm package to depend on at runtime and no JS bundler — Tailwind's CLI compiles one stylesheet, and Django serves it as an ordinary static file. {% endblock %} {% block doc_body %}

1. Install the apps

The design system is distributed as one pip-installable package (wise-design-system, providing the wise_core / wise_autocomplete / wise_richtext top-level packages) rather than copied in by hand. It isn't published to PyPI, so install it straight from this repository — pin to a commit or tag (...wise_design_system.git@<sha-or-tag>) rather than tracking a branch in a real project's requirements.txt: 

{% filter force_escape %}{% verbatim %}pip install "wise-design-system @ git+https://github.com/samiferr/wise_design_system.git"

# wise_autocomplete's AutocompleteInputWidget needs Django REST Framework - pull it
# in with the `autocomplete` extra instead of installing it separately:
pip install "wise-design-system[autocomplete] @ git+https://github.com/samiferr/wise_design_system.git"{% endverbatim %}{% endfilter %}

This pulls in Django and django-filter automatically. wise_core is the only required app — register the ones you actually use: 

{% filter force_escape %}{% verbatim %}INSTALLED_APPS = [
    # ...
    'django.contrib.humanize',   # used by some generic templates
    'django_filters',            # required by WiseListView's filtering
    'rest_framework',            # only if you use AutocompleteInputWidget

    'wise_core',
    'wise_autocomplete',         # optional
    'wise_richtext',             # optional
]{% endverbatim %}{% endfilter %}
Vendoring a copy (or a git submodule) into your project still works, if you'd rather patch the design system in place — nothing here depends on it being pip-installed specifically. Step 3 below covers both cases, since they build the stylesheet differently.

2. Register the context processor

wise_core.context_processors.nav feeds the sidebar menu from a plain setting. Skip it only if you never render nav_menu.html. 

{% filter force_escape %}{% verbatim %}TEMPLATES = [{
    'BACKEND': 'django.template.backends.django.DjangoTemplates',
    'APP_DIRS': True,
    'OPTIONS': {'context_processors': [
        'django.template.context_processors.request',   # required
        'django.contrib.auth.context_processors.auth',
        'django.contrib.messages.context_processors.messages',
        'wise_core.context_processors.nav',
    ]},
}]{% endverbatim %}{% endfilter %}

3. Build the stylesheet

Tailwind v4 needs to scan your templates (@source) to know which utility classes to generate, so every project builds its own tailwind.css — there is no universal precompiled stylesheet to just link to. wise_core/static/wise_core/css/tokens.css is a partial: the @theme tokens and @layer components rules, with no @import "tailwindcss" and no @source of its own.

Your project's own entry CSS file supplies both. @source/@import paths are resolved relative to the CSS file that names them — which means the path you write depends on how wise_core got onto disk. Since step 1 installed it with pip, it lives wherever your virtualenv put it (.venv/lib/python3.X/site-packages/wise_core/… or similar) — not at a fixed location relative to your project — so a hardcoded ../../wise_core/… path will resolve to nothing, or to the wrong thing, on a teammate's machine or in CI.

3a. Point Tailwind at wise_core — pip-installed (the default)

Resolve the install location at build time instead of hardcoding it. A tiny Python script asks importlib where each wise_* package actually lives and writes the @source/@import lines for it into a generated partial, which your checked-in input.css then imports: 

{% filter force_escape %}{% verbatim %}# static_src/generate_wise_sources.py
# Run before every Tailwind build (see the npm hooks below). Writes absolute
# @source/@import lines for whichever wise_* packages are actually installed,
# so input.css itself stays a portable, checked-in file with no
# environment-specific paths in it.
import importlib.util
from pathlib import Path

OUT = Path(__file__).parent / "_wise_sources.css"

lines = []
for package in ["wise_core", "wise_autocomplete", "wise_richtext"]:
    spec = importlib.util.find_spec(package)
    if spec is None or not spec.submodule_search_locations:
        continue
    package_dir = Path(spec.submodule_search_locations[0])
    lines.append(f'@source "{package_dir / "templates"}";')

tokens_spec = importlib.util.find_spec("wise_core")
if tokens_spec and tokens_spec.submodule_search_locations:
    tokens_path = Path(tokens_spec.submodule_search_locations[0]) / "static/wise_core/css/tokens.css"
    lines.append(f'@import "{tokens_path}";')

OUT.write_text("\n".join(lines) + "\n"){% endverbatim %}{% endfilter %}
{% filter force_escape %}{% verbatim %}/* static_src/input.css - checked in, no absolute paths */
@import "tailwindcss";
@import "./_wise_sources.css";   /* generated - gitignore it */

@source "../myapp/templates";{% endverbatim %}{% endfilter %}

Then wire those two scripts into package.json:

{% filter force_escape %}{% verbatim %}{
  "scripts": {
    "prebuild:css": "python static_src/generate_wise_sources.py",
    "build:css": "tailwindcss -i ./static_src/input.css -o ./myapp/static/myapp/css/tailwind.css --minify",
    "prewatch:css": "python static_src/generate_wise_sources.py",
    "watch:css": "tailwindcss -i ./static_src/input.css -o ./myapp/static/myapp/css/tailwind.css --watch"
  }
}{% endverbatim %}{% endfilter %}
The generated _wise_sources.css is environment-specific — add it to .gitignore and let the prebuild:css/prewatch:css hook regenerate it on every machine and in CI, right before Tailwind runs.

3b. Point Tailwind at wise_core — vendored / git submodule

If you vendored a copy instead (see the callout in step 1), wise_core sits at a fixed path relative to your project, so a plain relative @import works with no generation step — this is what demo/static_src/input.css in this repo does, since wise_core is right there in the same checkout: 

{% filter force_escape %}{% verbatim %}/* static_src/input.css */
@import "tailwindcss";

/* Tell Tailwind where to scan for class names - including every wise_* app,
   since their component markup uses utility classes too. */
@source "../myapp/templates";
@source "../../wise_core/templates";
@source "../../wise_autocomplete/templates";
@source "../../wise_richtext/templates";

@import "../../wise_core/static/wise_core/css/tokens.css";{% endverbatim %}{% endfilter %}
Whichever case applies to you, forgetting an @source line is the single most common setup mistake: the build succeeds, but any utility class used only in that directory is tree-shaken out and the page renders unstyled.

3c. Install the Tailwind CLI and compile

{% filter force_escape %}{% verbatim %}npm install -D @tailwindcss/cli tailwindcss{% endverbatim %}{% endfilter %}

Run the build:css/watch:css scripts from 3a if you added them, or call the CLI directly — run once for a production build, or add --watch while developing so the CSS recompiles as you edit templates: 

{% filter force_escape %}{% verbatim %}npm run build:css      # one-off build
npm run watch:css      # rebuild automatically while you work

# or, without the npm scripts:
npx tailwindcss -i ./static_src/input.css \
                -o ./myapp/static/myapp/css/tailwind.css --minify{% endverbatim %}{% endfilter %}

Point {% templatetag openblock %} load static {% templatetag closeblock %} / your base template at that output file — wise_core/base.html already does this for you if you extend it in the next step.

3d. Customize colors, or build a theme of your own

Never edit tokens.css itself — that file belongs to the design system and gets overwritten on upgrade. Instead, add your own @theme block to input.css, after the wise_core import (whichever form from 3a/3b you used): Tailwind v4 merges @theme blocks by variable name, so whichever one is imported last wins. 

{% filter force_escape %}{% verbatim %}/* static_src/input.css */
@import "tailwindcss";
@import "./_wise_sources.css";   /* or the vendored @source/@import lines from 3b */

@source "../myapp/templates";

/* Imported AFTER wise_core's tokens, so these override it. */
@theme {
    --color-brand-500: #7c3aed;
    --color-brand-600: #6d28d9;
    --color-brand-700: #5b21b6;
    --color-action-500: #7c3aed;
    --color-action-600: #6d28d9;
    --color-action-700: #5b21b6;
}{% endverbatim %}{% endfilter %}

Adding a brand-new theme (as opposed to retuning the default one) works the same way, but with an attribute selector instead of a bare @theme block — add this and wiseSetTheme('sepia') switches to it with no other wiring needed: 

{% filter force_escape %}{% verbatim %}:root[data-theme="sepia"] {
    --color-page: #f4ecd8;
    --color-panel: #fbf6ea;
    --color-gray-900: #3b2f1c;
}{% endverbatim %}{% endfilter %}

Rebuild (step 3c) after any token change — Tailwind has to re-scan and re-emit tailwind.css before the new values show up. For rounded corners, overriding a component's own CSS rule, and checking contrast when you retune a color ramp, see Customizing & Theming.
