There is no client-side state: each tab is a link to its own URL, and the server marks one .selected. That means tabs are bookmarkable, back-button friendly, and each panel only loads the data it needs. {% endblock %} {% block doc_body %}

Use cases

  • Switching between server-rendered views of the same record - an Overview/History/Settings split on a detail page.
  • A record's tabs where each tab should be bookmarkable, shareable, and survive a page refresh - since each tab is its own URL.
  • A tab whose panel is expensive to query - only the active tab's view pays for its own database queries.
  • Not for client-side-only panels with no separate URL per tab - that hides data behind CSS and reloads everything on every page load regardless of which tab is open.

The views behind them

One view per tab, each rendering the same shell. A shared base view keeps the tab bar and the record lookup in one place. 

{% filter force_escape %}{% verbatim %}# views.py
class CategoryTabMixin(WiseDetailView):
    model = Category

class CategoryOverviewView(CategoryTabMixin):
    template_name = 'showcase/category/overview.html'

class CategoryProductsView(CategoryTabMixin):
    template_name = 'showcase/category/products.html'

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['products'] = self.object.products.all()   # only this tab pays for it
        return context

# urls.py
path('categories//', CategoryOverviewView.as_view(), name='category_overview'),
path('categories//products/', CategoryProductsView.as_view(), name='category_products'),{% endverbatim %}{% endfilter %}

Why not client-side panels?

{% lucide "info" size=16 cls="callout-icon" %}
Hiding panels with CSS means every tab's data is queried and rendered on every page load, even the ones nobody opens — and the URL no longer says which tab you are on, so a bookmark or a refresh drops you back on the first. One URL per tab avoids both.
