Driven by WiseListView + django-filter, so the queryset stays the source of truth and the browser only ever receives one page of rows. {% endblock %} {% block doc_body %}

Use cases

  • Any list of records that needs pagination, filtering, or sorting - offered as the ?view=table alternative on a model's list page, which renders a card list by default.
  • A page where the row count could grow past what fits comfortably on screen, and the queryset should stay the source of truth (only one page of rows ever reaches the browser).
  • Adding sortable columns or row-level actions (edit/delete/dropdown menu) to an existing list view.
  • Not the right fit for a small, fixed set of dashboard tiles or a card-style picker - use the Card component for that instead. A list page ships both anyway, via the Card list vs Data table view toggle.

A table always sits in a card: <div class="card card-table mt-4 overflow-x-auto"> around the <table class="data-table">. The card is flush, so the table meets its edges, and it scrolls the table sideways when it is too wide (a table is the one thing that cannot reflow to a narrow screen). There is no card header: the page's actions stay in the page header. The pager goes in a .card-footer - Lumen's pagination, rendered by _pagination.html. See Pagination.

ID column

When a record's primary key is something people actually look up — a support ticket reference, an API identifier, a value someone reads out over the phone — give it its own column, first, narrow and muted so it doesn't compete with the row's real content: 

{% filter force_escape %}{% verbatim %}ID
...
{{ item.pk }}{% endverbatim %}{% endfilter %}

It's opt-in per table, not automatic — skip it for internal-only lists where the ID is never something a person needs to reference.

Row actions

One trigger, not a row of icon buttons. Past two or three actions, inline btn-ghost icons compete with each other and with the row's own content — a dropdown keeps the row scannable and gives every action a text label instead of a tooltip. The trigger is a plain vertical-dots btn-ghost — no border, so it doesn't read as its own boxed control competing with the row — and its column sits right after ID, before the record's own data, so actions are always in the same place regardless of how many data columns a table has:

Column ordering

Sorting is a query parameter, applied to the queryset — not a client-side re-sort, which would only reorder the current page and silently lie about the rest. Every sortable header's chevron sits at the right edge of the column, gray by default. Unsorted columns stay muted ({% lucide "chevrons-up-down" size=14 cls="inline align-[-2px] text-content-subdued" %}); the active column's chevron switches to the theme color ({% lucide "chevron-up" size=14 cls="inline align-[-2px] text-action-600" %}/{% lucide "chevron-down" size=14 cls="inline align-[-2px] text-action-600" %}) so the current sort reads at a glance.

{% filter force_escape %}{% verbatim %}class CategoryListView(WiseListView):
    model = Category
    sortable_fields = {"name", "created_at"}   # allowlist - never trust the raw param{% endverbatim %}{% endfilter %}

sortable_fields is WiseListView's own allowlist — it reads ?sort=name/?sort=-name, orders the queryset, and puts current_sort in the context, all without touching get_queryset() yourself. Render each header with the partial, and it renders the right icon and toggles direction on click automatically: 

{% filter force_escape %}{% verbatim %}{% load wise_tags %}
{% include 'wise_core/components/_sortable_th.html' with field='name' label='Name' %}{% endverbatim %}{% endfilter %}
{% status_glyph "notice" size=18 cls="callout-icon" %}
Allowlist the sortable fields
Passing request.GET["sort"] straight into order_by() lets a visitor order by any field or traverse relations — a slow-query and information-disclosure hazard. sortable_fields handles this for you on WiseListView; if you're building a sortable list outside it, allowlist the field yourself and always include a deterministic tiebreak (a final "pk"), or pagination will repeat and skip rows across pages.

{% filter force_escape %}{% verbatim %}{% include 'wise_core/components/_no_data.html' %}{% endverbatim %}{% endfilter %}

One row, one cell spanning every column. The partial reads the view's context and writes itself: the model's name, the "New" button (from create_url_name, only for a user who may add), and a different message with a Clear filters button when the list is empty because of the filter drawer rather than because there is nothing to show — see Empty State. The pager below it renders nothing while the list is empty, so the message doesn't sit above a dead "Page 1 / 1".

Row states

Rows follow Lumen's table: a 32px header and 40px rows (.data-table-compact 32px, .data-table-spacious 48px), 12px cell padding. A hovered row takes the translucent row-hover tint; a row marked .selected (or aria-selected="true") takes selected-subtle, one step stronger when hovered. Selection is never the tint alone - pair it with a checkbox or a check icon.
