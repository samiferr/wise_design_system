Use cases

  • Any numeric field backed by Django's IntegerField or DecimalField - quantity, price, age.
  • A field where the browser's own stepper (+/- arrows) and numeric keyboard on mobile are wanted.
  • Enforcing min/max/step bounds that the client and server agree on automatically, without repeating them in the template.
  • Not for a value that only looks numeric but isn't used arithmetically (e.g. a phone number or a code) - use a plain Input with an appropriate type/pattern instead.

min/max are a convenience, not a guarantee — they are trivially bypassed. Keep the validation on the field (min_value/max_value), which is what actually enforces it.

Money

Use DecimalField, never a float, and set step to the currency's smallest unit so the stepper doesn't produce unrepresentable values. 

{% filter force_escape %}{% verbatim %}price = forms.DecimalField(
    max_digits=9, decimal_places=2,
    widget=forms.NumberInput(attrs={"step": "0.01", "class": "input"}),
){% endverbatim %}{% endfilter %}

- Base markup: .
- Django's IntegerField/DecimalField already emit type="number" with min, max and step derived straight from the field's own validators (e.g. MinValueValidator, decimal_places) - let _form_fields.html render the field rather than hardcoding min/max/step by hand in the template, so client and server always agree on the bounds with nothing to keep in sync.
- Reuse the plain `.input` class - number inputs are not a separate visual component, only a different `type` attribute that changes the browser's keyboard and built-in stepper/validation.
- For a value that looks numeric but is never used arithmetically (a phone number, a postal code, an OTP digit), use a plain text Input (or the OTP Input component) instead of type="number" - that avoids the stepper arrows and locale-specific parsing quirks on values that aren't really numbers.{% endverbatim %}{% endfilter %}
