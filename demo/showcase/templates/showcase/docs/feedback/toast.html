Use cases

  • Confirming a just-completed action - a record was saved, an item was deleted, an email was sent.
  • Surfacing a non-blocking error or warning after a background action, without interrupting the page.
  • Any message that should appear briefly and dismiss itself - if it needs to persist on page load or be part of the document, use a Callout instead.
  • Almost always reached via Django's messages framework rather than built by hand - see the AI Prompt below.

The Django way

_messages.html is included once in base.html, so every page already renders whatever messages are pending. You only emit them. 

{% filter force_escape %}{% verbatim %}from django.contrib import messages

def publish(request, pk):
    product = get_object_or_404(Product, pk=pk)
    product.publish()
    messages.success(request, 'Product "%s" published.' % product.name)
    return redirect(product.get_absolute_url()){% endverbatim %}{% endfilter %}

The CRUD mixins do it for you from a success_message attribute — create or edit a Category to see one fire. 

{% filter force_escape %}{% verbatim %}class CategoryCreateView(WiseCreateView):
    model = Category
    form_class = CategoryForm
    success_message = 'Category "%(name)s" created.'{% endverbatim %}{% endfilter %}

    Auto-dismiss and accessibility

    {% lucide "alert-triangle" size=16 cls="callout-icon" %}
    Don't put irreplaceable information in a toast
    It disappears after six seconds and cannot be recalled. Validation errors belong on the field; anything the user may need to act on later belongs in the page. Add role="status" so screen readers announce it, and give error toasts no auto-dismiss at all.

    {% filter force_escape %}{% verbatim %}Use the Wise Design System's Toast for transient confirmations. In a Django app, do NOT hand-build the markup - use django.contrib.messages instead:
- In the view: from django.contrib import messages; messages.success(request, 'Product "%s" published.' % product.name)
- Available levels: messages.success (green), messages.error (red), messages.warning (amber), messages.info (neutral).

- Wise*View mixins (WiseCreateView, WiseUpdateView, WiseDeleteView) already emit a success message automatically from their success_message attribute - check whether the view already handles this before adding your own messages.success call.
