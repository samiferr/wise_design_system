The header row

list_generic.html's default list_actions is the whole standard row: the search box (when the view has a search filter), the filter button and the page's main "New" action. A list that only has rows to fill in overrides list_body and nothing else. On a phone the row spans the page: search and filter always share one line (the search field fills what the filter button leaves) and any other button wraps below.

Search

Free-text search is a filter of its own: a hidden q field on the FilterSet that ORs the columns worth searching. Because it is hidden it stays out of the filter drawer, and because WiseListView knows it is the search it is not counted as an applied filter (the button's badge) - and an empty result says "Nothing matches your search" rather than inviting a first record. 

{% filter force_escape %}{% verbatim %}class ProductFilter(django_filters.FilterSet):
    q = django_filters.CharFilter(method='search', label='Search', widget=forms.HiddenInput())
    name = django_filters.CharFilter(lookup_expr='icontains', label='Name')

    class Meta:
        model = Product
        fields = ['name', 'category']

    def search(self, queryset, name, value):
        return queryset.filter(Q(name__icontains=value) | Q(category__name__icontains=value)){% endverbatim %}{% endfilter %}

Another parameter name: set search_param on the view. The view hands the template can_search, search_query and search_active.

Filters open in a drawer

The filter button opens the Drawer (_filter.html), with the filter's fields rendered like every other form and Reset / Apply in its footer. Nothing to wire: wise_core/base.html includes it on every page that has a filter.

New is a floating button on a phone

{% filter force_escape %}{% verbatim %}{% include 'wise_core/components/_create_button.html' with label="New product" %}{% endverbatim %}{% endfilter %}

The page's main action is a normal primary button from the sm breakpoint up and, below it, a 56px floating action button at the bottom right (.btn-fab). It appears only when the view has a create_url (create_url_name on the view) and the visitor may add. One per page; secondary actions stay in the header row, which wraps.

Tables become cards on a phone

Every .data-table is, below sm, a list of cards - one per row, each cell a "label value" line - with no toggle and no second template. The labels are the column headers (data-label overrides one; data-label="" shows the value alone), sortable headers stay as a row of sort links above the cards, and a row-actions menu goes to the card's corner.
